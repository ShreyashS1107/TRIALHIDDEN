PART 1 — THE ACTIVE AI/ML RISK ENGINE & EXCLUDED RESEARCH TARGETS
========================================================================================================================

The AI/ML subsystem evaluates infrastructure project distress using a 3-month fixed-horizon point-in-time formulation
(predicting project health at horizon t + 3 months using data available strictly on or before reporting month t).

1.1 ACTIVE PILLARS IN THE OPERATIONAL RISK ENGINE:
-------------------------------------------------
1. Primary Pillar: schedule_delay_3m
   - Model Architecture : Tuned Random Forest (RF_02: 200 trees, max_depth=12, min_samples_leaf=5, sqrt features)
   - Calibration        : Formally calibrated using Platt Sigmoid Scaling (fitted strictly on Validation set)
   - Out-of-Time (OOT)  : ROC-AUC = 0.9723, PR-AUC = 0.9722, Brier Score = 0.0389, ECE = 0.0279
   - Operational Role   : Primary calibrated probability signal of operational deadline breach within 3 months.

2. Secondary Pillar 1: cost_overrun_state_3m
   - Model Architecture : Random Forest (Balanced class weighting: 200 trees, max_depth=12, min_samples_leaf=5)
   - Calibration        : Uncalibrated ranking risk score in [0.00, 1.00]
   - Out-of-Time (OOT)  : ROC-AUC = 0.9895, PR-AUC = 0.9881, Precision@Top10% = 99.74%, Lift = 3.13x
   - Operational Role   : Secondary risk signal measuring the likelihood of structural financial expansion (> original budget).

3. Secondary Pillar 2: schedule_revision_3m
   - Model Architecture : Logistic Regression (L2 regularization, Unweighted)
   - Calibration        : Uncalibrated ranking risk score in [0.00, 1.00]
   - Out-of-Time (OOT)  : ROC-AUC = 0.8264, PR-AUC = 0.0519, Precision@Top10% = 4.22%, Lift = 3.55x
   - Operational Role   : Early warning signal for administrative milestone rescheduling / target date revisions.

4. Integrated Multi-Dimensional Risk Index: selected_integrated_risk
   - Formulation        : Candidate B (Evidence-Weighted Architecture selected on Validation split)
   - Formula            : Integrated_Risk = (0.50 * schedule_delay_risk) + (0.35 * cost_overrun_risk) + (0.15 * schedule_revision_risk)
   - Nature             : Composite operational surveillance index in [0.00, 1.00] (NOT a calibrated univariate probability)
   - Out-of-Time (OOT)  : Schedule Delay ROC = 0.9559 | Cost Overrun ROC = 0.8921 | Schedule Revision ROC = 0.7466

5. Operational Risk Bands: risk_band
   - Tiers              : LOW [0.00, 0.30), MODERATE [0.30, 0.60), HIGH [0.60, 0.80), VERY_HIGH [0.80, 1.00]
   - Monotonicity       : Strictly monotonic increasing empirical failure rates on untouched OOT holdout.

6. Risk Attribution & Dominance: dominant_component & component contributions
   - Components         : schedule_contribution (50% wt), cost_contribution (35% wt), schedule_revision_contribution (15% wt)
   - Dominant Output    : Identifies whether Schedule Delay, Cost Overrun, or Schedule Revision is the largest mathematical contributor.

1.2 STRICTLY EXCLUDED TARGET (DO NOT DISPLAY / DO NOT USE):

PART 2 — DEFINITIVE USER-FACING ML OUTPUT SPECIFICATION
========================================================================================================================

The machine learning pipeline outputs a standardized tabular dataset (ml/risk_engine/integrated_risk_scores.csv).
The frontend must accurately display each of the following ML fields:

------------------------------------------------------------------------------------------------------------------------
1. Field Name: schedule_delay_risk
   - Display Label      : "Schedule Delay Risk (3-Month)"
   - Simple Meaning     : Model-estimated probability that the project will experience an operational schedule delay over the next 3 months.
   - Expected Range     : [0.0000, 1.0000] (or 0.0% to 100.0%)
   - Output Nature      : Calibrated Probability (Sigmoid / Platt scaling on RF_02)
   - Operational Index? : No, this is a formal calibrated statistical probability.
   - User Display       : YES. Direct numeric percentage / gauge / progress bar.
   - Explanatory Text   : "Calibrated probability of project breaching original completion date within the next 3 months."

2. Field Name: cost_overrun_risk
   - Display Label      : "Cost Overrun Risk (3-Month)"
   - Simple Meaning     : Model-estimated risk score indicating the likelihood of the project being in a cost overrun state (> original sanctioned cost) at the 3-month horizon.
   - Expected Range     : [0.0000, 1.0000] (or 0.0 to 1.0 ranking score)
   - Output Nature      : Risk Score / Continuous Model Score (Random Forest Balanced)
   - Operational Index? : No, uncalibrated model score.
   - User Display       : YES. Continuous risk indicator / score.
   - Explanatory Text   : "Model risk score indicating probability of project exceeding original sanctioned budget within 3 months."

3. Field Name: schedule_revision_risk
   - Display Label      : "Schedule Revision Risk (3-Month)"
   - Simple Meaning     : Model-estimated early warning score indicating likelihood that authorities will formally revise/extend the project deadline within the next 3 months.
   - Expected Range     : [0.0000, 1.0000] (or 0.0 to 1.0 ranking score)
   - Output Nature      : Risk Score / Administrative Warning Signal (Logistic Regression)
   - Operational Index? : No, uncalibrated model score.
   - User Display       : YES. Secondary warning indicator.
   - Explanatory Text   : "Early warning score for upcoming administrative deadline extensions or completion date revisions."

4. Field Name: selected_integrated_risk (or integrated_risk)
   - Display Label      : "Integrated Risk Index"
   - Simple Meaning     : Multi-dimensional composite surveillance index synthesizing schedule delay, financial expansion, and administrative rescheduling risks into a single unified triage score.
   - Expected Range     : [0.0000, 1.0000] (Index score from 0.00 to 1.00)
   - Output Nature      : Composite Operational Index: (0.50 * Schedule) + (0.35 * Cost) + (0.15 * Schedule Revision)
   - Operational Index? : YES. This is explicitly an operational prioritization index, NOT a single univariate probability.
   - User Display       : YES. Primary project sorting metric, portfolio heatmaps, and project detail risk headers.
   - Explanatory Text   : "Composite multi-dimensional surveillance index for prioritization and executive review."

5. Field Name: risk_band
   - Display Label      : "Operational Risk Tier" / "Risk Band"
   - Simple Meaning     : Operational triage category classifying project monitoring urgency.
   - Expected Values    : 'LOW', 'MODERATE', 'HIGH', 'VERY_HIGH'
   - Output Nature      : Categorical Classification / Triage Tier
   - Operational Index? : YES. Thresholded operational band.
   - User Display       : YES. Prominent status badge / tag across all views.
   - Explanatory Text   :
     * LOW       : Score < 0.30 (Low combined risk signals; project progressing within sanctioned baseline)
     * MODERATE  : 0.30 <= Score < 0.60 (Emerging risk signals; requires routine surveillance)
     * HIGH      : 0.60 <= Score < 0.80 (Elevated combined risk signals; requires close management review)
     * VERY_HIGH : Score >= 0.80 (Strongest combined distress signals; requires immediate executive intervention)

6. Field Name: dominant_component
   - Display Label      : "Primary Risk Component" / "Dominant Factor"
   - Simple Meaning     : The specific risk pillar contributing the largest numerical share to the project's integrated risk score.
   - Expected Values    : 'Schedule Delay', 'Cost Overrun', 'Schedule Revision'
   - Output Nature      : Categorical Label derived from max(schedule_contrib, cost_contrib, srev_contrib)
   - Operational Index? : N/A (Analytical attribution)
   - User Display       : YES. Displayed alongside risk scores to highlight the primary distress dimension.
   - Explanatory Text   : "Indicates which risk dimension (Schedule, Cost, or Revision) contributes most heavily to the overall index."

7. Field Names: schedule_contribution, cost_contribution, schedule_revision_contribution
   - Display Labels     : "Schedule Component Weight", "Cost Component Weight", "Revision Component Weight"
   - Simple Meaning     : The weighted contribution of each component to the integrated risk score:
                          - schedule_contribution = 0.50 * schedule_delay_risk
                          - cost_contribution = 0.35 * cost_overrun_risk
                          - schedule_revision_contribution = 0.15 * schedule_revision_risk
   - Expected Range     : [0.0000, 0.5000] for Schedule, [0.0000, 0.3500] for Cost, [0.0000, 0.1500] for Schedule Revision.
   - Output Nature      : Numerical component breakdown (sums exactly to selected_integrated_risk).
   - User Display       : YES. Suitable for stacked bar charts, waterfall breakdowns, or radar charts.

8. Field Names: schedule_contrib_pct, cost_contrib_pct, schedule_rev_contrib_pct
   - Display Labels     : "Schedule Attribution (%)", "Cost Attribution (%)", "Revision Attribution (%)"
   - Simple Meaning     : Normalized percentage share of total risk generated by each pillar (sums to 100%).
   - Expected Range     : [0.0%, 100.0%]
   - Output Nature      : Percentage Breakdown
   - User Display       : YES. Suitable for pie charts / breakdown tooltips.

PART 3 — CRITICAL DISTINCTION: PREDICTIVE RISK SIGNALS VS FACTUAL EXPLANATIONS
========================================================================================================================

The frontend development team MUST understand the fundamental distinction between a PREDICTIVE RISK SIGNAL and a
FACTUAL CAUSAL REASON.

3.1 WHAT THE ML SYSTEM ACTUALLY OUTPUTS:
---------------------------------------
The ML system measures statistical risk signals based on mathematical patterns in project trajectories:
- Schedule Delay Risk (0.98) means: "The project's timeline runway, construction velocity, and historical progress rate
  strongly match patterns of projects that fail to complete within 3 months."
- Cost Overrun Risk (0.85) means: "The project's financial expenditure pace and baseline cost structure indicate an 85%
  statistical affinity with projects operating in budget overrun."
- Dominant Component ("Schedule Delay") means: "Schedule delay accounts for the largest proportion of this project's
  calculated integrated risk score."

3.2 WHAT THE ML SYSTEM DOES NOT OUTPUT (UNSUPPORTED REAL-WORLD CAUSES):
----------------------------------------------------------------------
The PAIMANA dataset does NOT contain structured causal incident logs. The ML models DO NOT know and CANNOT determine:
- "Delay caused by contractor insolvency"
- "Stagnation due to environmental litigation"
- "Cost overrun caused by raw material inflation"
- "Delay caused by state land acquisition disputes"
- "Work stopped due to monsoon / weather events"

3.3 MANDATORY INSTRUCTIONS FOR FRONTEND:
---------------------------------------
1. DO NOT create a UI section titled "Reasons for Project Delay" or "Why Project Failed" that invents causal stories.
2. DO NOT mislabel "dominant_component" as "Root Cause of Delay". Label it "Primary Risk Pillar" or "Dominant Score Component".
3. If an interpretability / breakdown card is built, show the THREE MATHEMATICAL RISK PILLARS (Schedule Delay, Cost Overrun,
   Schedule Revision) and engineered velocity/stagnation metrics, NOT fabricated natural language excuses.

PART 5 — PROJECT STATUS: THREE-LAYER SEPARATION
========================================================================================================================

The frontend must strictly preserve the distinction between RAW PROJECT FACTS, DERIVED ANALYTICS, and ML PREDICTIONS:

------------------------------------------------------------------------------------------------------------------------
LAYER A: RAW PROJECT FACTS (Reported Directly by MoSPI / PAIMANA)
------------------------------------------------------------------------------------------------------------------------
These are administrative figures reported directly by implementing ministries:
1. Physical Progress (%)                 : physical_progress_percent (e.g. 63.59%)
2. Cumulative Expenditure (₹ Cr)         : cumulative_expenditure_crore (e.g. ₹515.30 Cr)
3. Original Sanctioned Cost (₹ Cr)       : original_cost_crore (e.g. ₹517.05 Cr)
4. Revised / Anticipated Cost (₹ Cr)     : revised_cost_crore (e.g. ₹655.06 Cr)
5. Sanction Approval Date                : approval_start_date (e.g. 2021-09)
6. Original Completion Date (DOC)        : original_completion_date (e.g. 2022-09)
7. Latest Revised Completion Date        : revised_completion_date (e.g. 2024-09)
8. Actual Completion Date                : actual_completion_date (for Table 3 projects)
9. Report Monitoring Month               : report_month (e.g. 2025-04)

------------------------------------------------------------------------------------------------------------------------
LAYER B: DERIVED ANALYTICAL INDICATORS (Calculated Deterministically from Data)
------------------------------------------------------------------------------------------------------------------------
These are objective mathematical calculations computed from raw facts (NOT machine learning models):
1. Cost Escalation (₹ Cr)                : revised_cost_crore - original_cost_crore
2. Cost Escalation (%)                   : cost_escalation_pct_t = ((revised_cost - original_cost) / original_cost) * 100
3. Expenditure Ratio (%)                 : expenditure_ratio_pct_t = (cumulative_expenditure / original_cost) * 100
4. Remaining Physical Progress (%)       : remaining_physical_progress_t = 100.0 - physical_progress_t
5. Schedule Slippage (Months)            : schedule_slippage_months_t = months_between(revised_DOC, original_DOC)
6. Months to Original Deadline           : months_to_original_doc_t = months_between(original_DOC, report_month)
   (Negative value indicates project is already past original sanctioned deadline).
7. Planned Project Duration (Months)     : months_between(original_DOC, approval_start_date)
8. Current Project Age (Months)          : months_between(report_month, approval_start_date)
9. Progress Velocity (1-Month)           : progress_velocity_1m_t = progress(t) - progress(t-1)
10. Progress Velocity (3-Month Rolling)  : progress_velocity_3m_t = (progress(t) - progress(t-3)) / 3.0
11. Stagnation Indicator (3-Month)       : stagnant_3m_t (Flag: 1 if physical progress increased 0.0% over last 3 months)
12. Stagnation Streak (Months)           : months_since_last_progress_increase_t (Count of consecutive months at 0% change)
13. Expenditure vs Progress Divergence   : expenditure_ratio_pct_t - physical_progress_percent
    (Identifies capital burn outpacing physical site execution).

------------------------------------------------------------------------------------------------------------------------
LAYER C: MACHINE LEARNING RISK SIGNALS (Statistical Model Outputs)
------------------------------------------------------------------------------------------------------------------------
These are forward-looking predictive signals generated by trained AI/ML algorithms:
1. Schedule Delay Risk (3-Month)         : schedule_delay_risk (Calibrated probability [0.0, 1.0])
2. Cost Overrun Risk (3-Month)           : cost_overrun_risk (Continuous model score [0.0, 1.0])
3. Schedule Revision Risk (3-Month)      : schedule_revision_risk (Early warning score [0.0, 1.0])
4. Integrated Risk Index                 : selected_integrated_risk (Operational surveillance index [0.0, 1.0])
5. Operational Risk Band                 : risk_band (Categorical triage tier: LOW / MODERATE / HIGH / VERY_HIGH)
6. Dominant Risk Pillar                  : dominant_component (Primary mathematical risk driver)
7. Risk Pillar Contributions             : schedule_contribution, cost_contribution, schedule_revision_contribution

PART 14 — "DO NOT IMPLEMENT / DO NOT CLAIM" (MANDATORY RESTRICTIONS)
========================================================================================================================

To prevent misrepresentation and preserve system credibility during audits and evaluations, the frontend development
team is STRICTLY FORBIDDEN from implementing or claiming any of the following:

1. DO NOT CLAIM CAUSAL REASONS FOR DELAY:
   Never claim that the ML model has discovered why a project is delayed (e.g. "Model identified contractor dispute").
   The models evaluate numerical trajectory features, not qualitative causal narratives.

2. DO NOT USE cost_revision_event_3m AS AN ACTIVE RISK SIGNAL:
   This experimental target suffered a severe Out-of-Time generalization failure (OOT ROC-AUC = 0.4394) and was formally
   relegated to RESEARCH_ONLY. Do not expose it on the dashboard.

3. DO NOT CLAIM INTEGRATED RISK IS A CALIBRATED PROBABILITY:
   The Integrated Risk Index is an operational surveillance and triage index in [0, 1]. It is NOT a calibrated probability
   of overall project failure. (Only the primary schedule_delay_3m component is a calibrated probability).

4. DO NOT CLAIM RISK BANDS ARE OFFICIAL STATUTORY CLASSIFICATIONS:
   The Risk Bands (LOW, MODERATE, HIGH, VERY_HIGH) are operational triage tiers established for automated monitoring,
   not official statutory classifications issued by the Union Cabinet or MoSPI.

5. DO NOT PRESENT ML PREDICTIONS AS RAW GOVERNMENT FACTS:
   Always clearly separate reported facts (e.g. current physical progress = 63.59%) from predictive forecasts
   (e.g. model-predicted 3-month schedule delay probability = 76.82%).

6. DO NOT INVENT UNSUPPORTED DATA FIELDS:
   Do not add placeholders for contractor names, GPS coordinates, tender packages, sub-contractors, or land acquisition
   hectares unless provided by a verified backend API.

7. DO NOT USE FUTURE DATA IN HISTORICAL VIEWS (LOOKAHEAD LEAKAGE):
   When displaying a project at reporting month t (e.g. 2025-06), display risk scores and progress as of month t.
   Never display future months' progress as if it were known in the past.

PART 17 — FOUR-LAYER SYSTEM ARCHITECTURE CLASSIFICATION
========================================================================================================================

Every single frontend element belongs strictly to one of the following four architectural layers:

1. LAYER 1: RAW DATA (MoSPI PAIMANA Flash Report Extracted Facts)
   - Origin: Extracted directly from monthly government PDF tables (Table 6, Table 3, Table 4).
   - Transformation: Standardized units (₹ Crore, ISO YYYY-MM, % progress). Zero modeling.
   - Examples: project_id, project_name, agency, state, original_cost_crore, physical_progress_percent.

2. LAYER 2: DERIVED ANALYTICS (Deterministic Engineering Calculations)
   - Origin: Mathematical formulas computed from raw facts.
   - Transformation: Time differences, ratios, rolling velocities, stagnation counters. Zero ML inference.
   - Examples: cost_escalation_pct, expenditure_ratio_pct, months_to_original_doc, progress_velocity_3m, stagnant_3m_t.

3. LAYER 3: ML OUTPUTS (Trained AI/ML Predictive Models)
   - Origin: Frozen Random Forest, Logistic Regression, and Platt Calibrator pipelines.
   - Transformation: Multi-feature statistical inference evaluated on 79 point-in-time features.
   - Examples: schedule_delay_risk, cost_overrun_risk, schedule_revision_risk, selected_integrated_risk, risk_band.

4. LAYER 4: SYSTEM & UX FEATURES (Application Logic & Interactions)
   - Origin: Frontend / Backend web application runtime.
   - Transformation: Filtering, sorting, full-text search, pagination, session state, exports, chart rendering.
   - Examples: Multi-select state filter, dual-range risk slider, project comparison modal, CSV exporter.

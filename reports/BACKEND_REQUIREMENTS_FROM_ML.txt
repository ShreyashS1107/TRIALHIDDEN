PURPOSE OF THIS DOCUMENT:
This specification establishes the authoritative, binding requirements contract for the Backend Engineering and Data
Engineering teams. It defines the exact data structures, ingestion pipelines, machine learning model serving contracts,
79-feature calculation invariants, data validation rules, anomaly handling policies, and temporal safeguards necessary
to power the MoSPI/IPMD Integrated Project-Monitoring Platform (SIH26103).

CORE ARCHITECTURAL PRINCIPLES FOR BACKEND:
1. BACKEND DECOUPLING (BATCH-FIRST / CACHED SERVING):
   The backend web server (e.g. FastAPI / Node.js) MUST NOT execute synchronous heavy ML training, iterative cross-validation,
   or un-cached dynamic feature engineering inside the HTTP request-response cycle. All historical ML predictions are
   pre-computed into structured matrices (`integrated_risk_scores.csv`), and new monthly PDF ingestions are processed via
   asynchronous background worker pipelines (Celery / Redis / BackgroundTasks).
2. STRICT TEMPORAL INVARIANCE (ZERO LOOKAHEAD LEAKAGE):
   When computing derived analytics or serving historical snapshots as of month t, the backend MUST NEVER incorporate data
   from months > t. Future facts must never leak into historical views.
3. THREE-LAYER SYSTEM ISOLATION:
   The backend database and service layer must cleanly isolate:
   - Layer A: Raw Reported Facts (MoSPI Flash Reports),
   - Layer B: Deterministic Derived Analytics (Engineering metrics, velocities, stagnation counters),
   - Layer C: Predictive ML Risk Signals (Model inferences, Platt-calibrated probabilities, and integrated indices).
4. STRICT ML TARGET DISCIPLINE:
   The backend must strictly enforce the exclusion of the failed research target `cost_revision_event_3m` from all active
   production tables, API endpoints, alerts, and database columns.

PART 1 — THE ACTIVE AI/ML RISK ENGINE & MODEL ARTIFACT CONTRACT
========================================================================================================================

The AI/ML subsystem predicts project distress using a 3-month fixed-horizon point-in-time formulation (predicting project
health at horizon t + 3 months using data available strictly on or before reporting month t).

1.1 ACTIVE PILLARS & PRODUCTION MODEL ARTIFACTS:
------------------------------------------------
1. Primary Pillar: Schedule Delay Risk (`schedule_delay_3m`)
   - Target Definition   : Binary indicator. 1 if project experiences schedule delay (DOC > original DOC) at t + 3 months.
   - Model Architecture  : Tuned Random Forest Classifier (RF_02: 200 estimators, max_depth=12, min_samples_leaf=5, sqrt features).
   - Calibration Pipeline: Platt Sigmoid Scaling (fitted strictly on Validation set logits via LogisticRegression).
   - Serialized Artifact : `ml/calibration_final/rf02_calibrated.pkl` (or `ml/models/best_model_random_forest.joblib`).
   - Out-of-Time Metrics : ROC-AUC = 0.9723, PR-AUC = 0.9722, Brier Score = 0.0389, ECE = 0.0279.
   - Mathematical Output : Calibrated posterior probability P(Schedule_Delay = 1 | X_t) in range [0.0000, 1.0000].
   - Output Column Name  : `schedule_delay_risk` (Float64).

2. Secondary Pillar 1: Cost Overrun Risk (`cost_overrun_state_3m`)
   - Target Definition   : Binary indicator. 1 if project is in a cost overrun state (revised_cost > original_cost) at t + 3 months.
   - Model Architecture  : Random Forest Classifier with Balanced Class Weighting (200 estimators, max_depth=12, min_samples_leaf=5).
   - Serialized Artifact : `ml/secondary_targets/best_model_rf_cost_overrun_balanced.joblib`.
   - Out-of-Time Metrics : ROC-AUC = 0.9895, PR-AUC = 0.9881, Precision@Top10% = 99.74%, Lift = 3.13x.
   - Mathematical Output : Continuous model risk score in range [0.0000, 1.0000] (uncalibrated ranking score).
   - Output Column Name  : `cost_overrun_risk` (Float64).

3. Secondary Pillar 2: Schedule Revision Warning (`schedule_revision_3m`)
   - Target Definition   : Binary indicator. 1 if project experiences a formal administrative completion date revision at t + 3 months.
   - Model Architecture  : Regularized Logistic Regression (L2 penalty, unweighted, liblinear/lbfgs solver).
   - Serialized Artifact : `ml/secondary_targets/best_model_logreg_schedule_revision.joblib`.
   - Out-of-Time Metrics : ROC-AUC = 0.8264, PR-AUC = 0.0519, Precision@Top10% = 4.22%, Lift = 3.55x.
   - Mathematical Output : Continuous early warning score in range [0.0000, 1.0000].
   - Output Column Name  : `schedule_revision_risk` (Float64).

4. Multi-Dimensional Integrated Risk Index (`selected_integrated_risk`):
   - Formulation         : Candidate B (Evidence-Weighted Architecture selected on Validation split).
   - Exact Formula       :
     selected_integrated_risk = (0.50 * schedule_delay_risk) + (0.35 * cost_overrun_risk) + (0.15 * schedule_revision_risk)
   - Nature              : Composite operational surveillance and triage index in [0.0000, 1.0000].
   - Backend Requirement : Must be computed deterministically if scoring new snapshots, or loaded directly from the matrix.

5. Risk Band Classification (`risk_band`):
   - Categorical Triage  :
     * 'LOW'       : selected_integrated_risk < 0.30
     * 'MODERATE'  : 0.30 <= selected_integrated_risk < 0.60
     * 'HIGH'      : 0.60 <= selected_integrated_risk < 0.80
     * 'VERY_HIGH' : selected_integrated_risk >= 0.80
   - Monotonicity Invariant: Strictly verified against empirical holdout delay rates (LOW: 0.08% -> VERY_HIGH: 97.73%).

6. Risk Attribution & Dominance (`dominant_component` & Contributions):
   - `schedule_contribution`          = 0.50 * schedule_delay_risk
   - `cost_contribution`              = 0.35 * cost_overrun_risk
   - `schedule_revision_contribution` = 0.15 * schedule_revision_risk
   - `schedule_contrib_pct`           = (schedule_contribution / selected_integrated_risk) * 100.0  (if risk > 0 else 0)
   - `cost_contrib_pct`               = (cost_contribution / selected_integrated_risk) * 100.0      (if risk > 0 else 0)
   - `schedule_rev_contrib_pct`       = (schedule_revision_contribution / selected_integrated_risk) * 100.0
   - `dominant_component`             = Pillar corresponding to max(schedule_contribution, cost_contribution, schedule_revision_contribution)
                                        Values: 'Schedule Delay' | 'Cost Overrun' | 'Schedule Revision'

1.2 STRICTLY EXCLUDED TARGET (MANDATORY BACKEND BAN):
-----------------------------------------------------
- Excluded Target Name : `cost_revision_event_3m`
- Exclusion Reason     : Collapsed on Out-of-Time holdout (ROC-AUC = 0.4394, Lift = 0.56x) due to a 10x fiscal base-rate collapse
                         (21.9% event rate in April 2025 down to 0.9% in February 2026).
- Action Required      : DO NOT create database columns for this target. DO NOT write API serializers for it.
                         DO NOT trigger alerts based on it. Retain exclusively in offline ML research documentation.

PART 3 — CANONICAL IDENTIFIER RESOLUTION & LONGITUDINAL LINKING RULES
========================================================================================================================

A critical challenge discovered during PDF extraction is the transition between legacy MoSPI OCMS codes (e.g. `N04000106`)
and modern 6-digit PAIMANA project codes (e.g. `612786`).

3.1 IDENTIFIER RESOLUTION RULES:
--------------------------------
1. Canonical Key: Every project MUST resolve to a single canonical `project_id`.
2. Cross-Walk Mapping:
   - When a project reports under an 8-character OCMS code in legacy reports (April–June 2025) and later transitions to a
     6-digit PAIMANA code in newer reports (July 2025–June 2026), the backend mapping dictionary must resolve both identifiers
     to the canonical 6-digit ID.
   - 1,137 legacy OCMS codes have been successfully mapped to 6-digit PAIMANA codes.
3. Dual-Field Indexing:
   - The database must maintain unique indexing on `project_id` and a secondary non-unique lookup index on `legacy_ocms_code`.
   - API search queries for either `612786` or `N04000106` MUST return the identical unified project entity.

3.2 LONGITUDINAL INTEGRITY INVARIANTS:
--------------------------------------
1. EXACTLY ONE SNAPSHOT PER MONTH: For any given `(project_id, report_month)`, there must exist exactly one record.
2. IMMUTABLE HISTORICAL SNAPSHOTS: Ingesting a new month's Flash Report must INSERT new records for `report_month = t_new`.
   It MUST NEVER overwrite, alter, or back-propagate values into previous reporting months (`report_month < t_new`).
3. TIME-SERIES GAP HANDLING: If a project drops out of Table 6 for 2 months and reappears in month 3, the missing months
   must remain unrecorded (or marked as non-reporting). The backend must NOT synthesize fake interpolated rows.

PART 4 — DATA VALIDATION, QUALITY AUDITS & ANOMALY HANDLING CONTRACT
========================================================================================================================

Real-world government infrastructure reporting contains data anomalies and reporting noise. The data engineering pipeline
established strict validation rules implemented in `scripts/validate_paimana_dataset.py`. The backend must enforce these:

4.1 MANDATORY INGESTION VALIDATION RULES:
-----------------------------------------
1. Physical Progress Bounds: `0.0 <= physical_progress_percent <= 100.0`. If a value > 100.0 is encountered (e.g. OCR error 100.5%),
   bound it to 100.0 and emit a validation warning.
2. Financial Non-Negativity: `original_cost_crore >= 0.0`, `revised_cost_crore >= 0.0`, `cumulative_expenditure_crore >= 0.0`.
   Negative financial figures must be quarantined for audit.
3. Date Format Enforcement: All dates must conform strictly to `YYYY-MM` or standard ISO-8601 strings.
4. Duplicate Key Assertion: Ingestion jobs must abort and rollback if duplicate `(project_id, report_month)` keys are detected.

4.2 THE 1,868 MANUAL-REVIEW AUDIT ROWS POLICY (`reports/manual_review.csv`):
----------------------------------------------------------------------------
- Background: In the master dataset of 21,555 rows, exactly 1,868 rows (8.66%) were flagged with trajectory anomalies:
  * Sudden Physical Progress Drop (>25% reduction month-over-month) due to scope revisions or contractor remeasurements.
  * Cumulative Expenditure Drop (>50% drop) caused by accounting adjustments or de-allocations.
  * Massive Cost Revisions (>400% budget change) caused by mega-package restructuring.
- MANDATORY BACKEND DIRECTIVE:
  * DO NOT DROP OR DELETE THESE 1,868 ROWS. Deleting them introduces severe survival and reporting selection bias into the platform.
  * Store diagnostic flags in a dedicated audit log table (`data_anomalies_log`) with foreign key reference to `(project_id, report_month)`.
  * Expose an optional data quality indicator in the project detail API response (`data_quality_flags: ["PROGRESS_REGRESSION_FLAG"]`).

PART 5 — DETERMINISTIC LAYER B DERIVED ANALYTICS ENGINE
========================================================================================================================

The backend must calculate Layer B derived analytics deterministically from raw Layer A facts. These metrics provide essential
real-time operational insight without requiring machine learning inference.

------------------------------------------------------------------------------------------------------------------------
METRIC NAME                 FIELD IDENTIFIER                     EXACT MATHEMATICAL FORMULA / LOGIC
------------------------------------------------------------------------------------------------------------------------
Cost Escalation (₹ Cr)      `cost_escalation_crore`              revised_cost_crore - original_cost_crore
Cost Escalation (%)         `cost_escalation_percent`            ((revised_cost - original_cost) / original_cost) * 100.0
                                                                 (Return 0.0 if original_cost == 0)
Expenditure Ratio (%)       `expenditure_ratio_percent`          (cumulative_expenditure / original_cost) * 100.0
Remaining Progress (%)      `remaining_physical_progress`        100.0 - physical_progress_percent
Schedule Slippage (Months)  `schedule_slippage_months`           months_between(revised_completion_date, original_completion_date)
                                                                 (Return 0.0 if revised_completion_date is Null)
Months to Original Deadline `months_to_original_doc`             months_between(original_completion_date, report_month)
                                                                 (Negative value indicates project is past original deadline)
Project Age (Months)        `project_age_months`                 months_between(report_month, approval_start_date)
Planned Duration (Months)   `planned_duration_months`            months_between(original_completion_date, approval_start_date)
1-Month Progress Velocity   `progress_velocity_1m`               progress(t) - progress(t-1)
                                                                 (Null if t-1 snapshot does not exist)
3-Month Rolling Velocity    `progress_velocity_3m`               (progress(t) - progress(t-3)) / 3.0
                                                                 (Fallback to 2-month or 1-month average if 3 months unavailable)
Stagnation Flag (3-Month)   `stagnant_3m_flag`                   1 if (progress(t) - progress(t-3) == 0.0) else 0
Stagnation Streak (Months)  `months_since_last_progress_increase` Count of consecutive months preceding t where delta_progress == 0
Spend vs Progress Diff      `expenditure_progress_divergence`    expenditure_ratio_percent - physical_progress_percent
------------------------------------------------------------------------------------------------------------------------

HELPER SPECIFICATION: `months_between(date_str_1, date_str_2)`
- Logic: `(year_1 - year_2) * 12 + (month_1 - month_2)` where dates are parsed from ISO `YYYY-MM`.

7.1 INFERENCE SERVING PATTERNS:
-------------------------------
The backend must support two complementary inference access modes:

MODE A: PRE-COMPUTED RISK MATRIX ACCESS (Standard Production Path)
- Implementation: Ingest `ml/risk_engine/integrated_risk_scores.csv` directly into the PostgreSQL `ml_risk_scores` table.
- Operation: Web API endpoints query indexed risk score rows directly by `(project_id, report_month)`.
- Query Latency SLA: < 10ms at p99. Zero ML compute overhead.

MODE B: ASYNCHRONOUS BATCH INFERENCE WORKER (For New Monthly PDF Reports)
- Trigger: An administrative user or automated cron triggers ingestion of a new Flash Report PDF (e.g. `FlashReport_July_2026.pdf`).
- Execution Flow:
  1. Worker executes PDF extraction (`scripts/extract_pdfs.py`) -> extracts raw Table 6 rows.
  2. Worker validates and merges raw rows into `monthly_snapshots` table for `report_month = '2026-07'`.
  3. Worker executes Point-in-Time feature pipeline (`features/build_features_v1.py`) using records <= 2026-07.
  4. Worker loads serialized model pipelines:
     - `rf02_calibrated.pkl` -> generates `schedule_delay_risk`
     - `best_model_rf_cost_overrun_balanced.joblib` -> generates `cost_overrun_risk`
     - `best_model_logreg_schedule_revision.joblib` -> generates `schedule_revision_risk`
  5. Worker computes `selected_integrated_risk`, `risk_band`, `dominant_component`, and component contributions.
  6. Worker bulk-inserts predictions into `ml_risk_scores` table and refreshes Redis caches.
- Processing Latency SLA: < 60 seconds for full portfolio batch inference (2,000+ projects).

PART 8 — MODEL INTERPRETABILITY & ATTRIBUTION REQUIREMENTS
========================================================================================================================

The backend API must deliver structured, mathematically sound risk breakdowns. It must strictly comply with the following:

8.1 MATHEMATICAL BREAKDOWN ENDPOINT REQUIREMENTS:
-------------------------------------------------
Every risk score payload returned by the backend MUST provide both absolute contributions and relative percentages:
- `schedule_contribution`          : Float in [0.0000, 0.5000]
- `cost_contribution`              : Float in [0.0000, 0.3500]
- `schedule_revision_contribution` : Float in [0.0000, 0.1500]
- `selected_integrated_risk`       = schedule_contribution + cost_contribution + schedule_revision_contribution
- `schedule_contrib_pct`           = (schedule_contribution / selected_integrated_risk) * 100.0
- `cost_contrib_pct`               = (cost_contribution / selected_integrated_risk) * 100.0
- `schedule_rev_contrib_pct`       = (schedule_revision_contribution / selected_integrated_risk) * 100.0
- `dominant_component`             = 'Schedule Delay' | 'Cost Overrun' | 'Schedule Revision'

8.2 FEATURE DRIVER ATTRIBUTION CONTRACT:
----------------------------------------
To explain why a project received high risk, the backend must expose top numerical feature drivers:
1. `months_to_original_doc` : (e.g. -14 months past deadline -> strong driver of schedule risk).
2. `progress_velocity_3m`   : (e.g. 0.0% / month -> strong driver of schedule stagnation).
3. `cost_escalation_percent`: (e.g. +45.2% budget growth -> strong driver of cost overrun risk).
4. `expenditure_divergence` : (e.g. 95% budget spent vs 50% physical progress -> capital burn driver).

8.3 STRICT CAUSAL PROHIBITION FOR BACKEND:
------------------------------------------
- The backend MUST NOT generate, store, or return synthetic natural language explanations that attribute delays to
  physical real-world causes (e.g. "Delay due to environmental clearances", "Contractor insolvency").
- The database schema must not include fields like `delay_root_cause_text` or `llm_generated_delay_excuse`.
